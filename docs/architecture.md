# Архитектура

Документ описывает устройство проекта и причины принятых решений.

## Общая схема

```text
Браузер
   │
   ▼
Nginx ──── /static/, /media/ ──► volumes
   │
   ▼ proxy_pass
Gunicorn → Django 5.2 + django CMS 5.0
   │
   ▼
PostgreSQL 17
```

В development Nginx отсутствует: `runserver` отдаёт и страницы, и статику.

## Разделение ответственности

Проект разделён на четыре приложения. Границы проведены по предметным областям,
а не по техническим слоям.

### `core`

Общая инфраструктура, не относящаяся к конкретной предметной области:

- абстрактные модели `TimeStampedModel`, `OrderedModel`, `SeoModel`;
- абстрактная база CMS-плагинов `SectionPluginBase` (заголовок, подзаголовок, якорь);
- `SiteSettings` — singleton с названием сайта, значениями SEO по умолчанию и
  настройками индексации;
- `CtaPluginModel` — единственный плагин без собственных данных;
- health-check, `robots.txt`, sitemap, обработчики 404 и 500;
- context processor `site_context`;
- template tags SEO и структурированных данных;
- команда `seed_demo`.

### `portfolio`

Ядро сайта: `DeveloperProfile`, `SkillCategory`, `Skill`, `ProjectCategory`,
`Project`, `MiniProject`, `Experience`, `Education`, `Certificate`, `SocialLink`
и восемь CMS-плагинов, отображающих эти данные.

### `blog`

`Category`, `Tag`, `Article` и плагин последних статей. Публикация управляется
парой полей `status` + `published_at`, а не отдельной моделью.

### `contact`

`ContactMessage`, форма, представление и плагин контактного блока.

## Ключевые решения

### Настройки разделены на четыре модуля

`base.py` содержит общее, остальные три модуля переопределяют только различия.
Production не имеет небезопасных fallback: отсутствие `DJANGO_SECRET_KEY`,
`DJANGO_ALLOWED_HOSTS` или `DJANGO_CSRF_TRUSTED_ORIGINS` останавливает запуск.
Development намеренно не включает HSTS: браузер запомнил бы принудительный HTTPS
для `localhost` и сломал бы локальную разработку по HTTP.

### CMS управляет композицией, приложения — данными

Плагины не дублируют доменные модели. Каждый плагин хранит только параметры
отображения (заголовок, лимит, флаги) и при необходимости ссылку на
существующий объект. Данные выбираются в `render()` актуальным queryset.

Следствие: чтобы поменять состав или порядок блоков на главной, Python-код
трогать не нужно — достаточно плейсхолдеров `hero`, `sections` и `closing` в
`cms/home.html`.

`SkillCategoriesPluginModel` — единственный плагин с M2M, поэтому у него
определён `copy_relations()`: без него django CMS потерял бы выбор категорий
при копировании страницы.

### URL: фиксированные префиксы вместо apphooks

Разделы приложений смонтированы на стабильных префиксах (`/about/`,
`/projects/`, `/tools/`, `/resume/`, `/blog/`, `/contacts/`), а django CMS
обрабатывает всё остальное своим catch-all. Это проще apphooks и не завязывает
маршрутизацию на конкретную страницу CMS, которую редактор может переименовать
или удалить.

Разделы обёрнуты в `i18n_patterns(prefix_default_language=False)`: русский
остаётся без префикса, английский появится на `/en/` без изменения URL-схемы.

### Готовность к английской версии

- `LANGUAGES` и `CMS_LANGUAGES` уже содержат `ru` и `en` с fallback на русский;
- весь интерфейсный текст в шаблонах обёрнут в `{% trans %}`;
- `LOCALE_PATHS` указывает на `src/locale/`.

Добавление английской версии — это `makemessages`, перевод и публикация
страниц, а не изменение архитектуры. Содержимое моделей (названия проектов,
тексты статей) при этом не переводится: для этого потребовалось бы отдельное
решение — например, `django-parler` или дублирующие поля.

### Публикация и черновики

- `Project.is_published` и `Article.status` + `published_at` фильтруются
  методами queryset `.published()`;
- эти же queryset используются в представлениях, плагинах и sitemap, поэтому
  черновик не может протечь ни на страницу, ни в поисковую выдачу;
- страницы CMS используют собственный механизм версионирования django CMS 5.

### Инварианты на уровне базы

Проверки, которые нельзя обойти в обход ORM:

| Ограничение | Смысл |
|-------------|-------|
| `unique_skill_per_category` | навык не дублируется внутри категории |
| `project_finished_after_started` | дата завершения не раньше даты начала |
| `experience_finished_after_started` | то же для опыта работы |
| `experience_current_has_no_end` | текущее место работы не имеет даты окончания |
| `education_finished_after_started` | то же для образования |

Singleton-модели (`SiteSettings`, `DeveloperProfile`) ограничены на уровне
`clean()` и `has_add_permission()`, а не базы: единственность здесь —
соглашение интерфейса, а не инвариант данных.

### Производительность

- `ProjectQuerySet.with_related()` и `ArticleQuerySet.with_related()` собирают
  `select_related` и `prefetch_related` в одном месте;
- плагин категорий навыков использует `Prefetch`, поэтому число запросов не
  растёт с числом категорий;
- `site_context` кеширует результат на объекте запроса, поэтому шапка и подвал
  стоят три запроса на страницу независимо от числа блоков;
- админка `SkillCategoryAdmin` считает навыки аннотацией, а не запросом на
  строку;
- кеширование страниц не включено: границы инвалидации при редактировании через
  CMS ещё не определены.

### Безопасность

- секреты только из переменных окружения, `.env` не коммитится;
- контактная форма защищена honeypot-полем и cooldown в сессии — без Redis и
  внешних сервисов;
- `ContactMessage` нельзя создать через админку, только через публичную форму;
- тело обращения и метаданные клиента не выводятся в списке админки и не
  попадают в письмо-уведомление;
- структурированные данные сериализуются в Python и экранируют `<`, поэтому
  содержимое моделей не может закрыть тег `<script>`;
- `X_FRAME_OPTIONS = "SAMEORIGIN"` — требование django CMS, который рендерит
  редакторы плагинов в iframe; соответствующая проверка `security.W019`
  заглушена в production с обоснованием в коде.

### Frontend

Серверные шаблоны, один CSS-файл и один JS-файл. Тема переключается сменой
атрибута `data-theme` на `<html>`; выбор хранится в `localStorage`, а до первой
отрисовки применяется маленьким inline-скриптом, чтобы не было вспышки
неправильной темы. JavaScript отвечает только за тему и мобильное меню — без
него сайт остаётся полностью читаемым.

## Схема данных

```text
DeveloperProfile (1)
SiteSettings (1)

SkillCategory 1──* Skill *──* Project
                     │          │
                     │          *──1 ProjectCategory
                     │                     │
                     *──* Experience       *──* MiniProject

Education, Certificate, SocialLink — независимые справочники

Category 1──* Article *──* Tag

ContactMessage — независимая таблица обращений
```

## Тестирование

`tests/unit/` проверяет модели, формы, template tags и настройки;
`tests/integration/` — представления, CMS-плагины, страницы CMS, контактную
форму, инфраструктурные endpoint и регистрацию в админке.

Тесты идут на PostgreSQL — на том же движке, что и production, поэтому
ограничения базы (`CheckConstraint`, `UniqueConstraint`), типы полей и
поведение транзакций проверяются по-настоящему, а не на приблизительной замене.
Базу поднимает `infra/compose/compose.test.yml`: данные лежат в tmpfs,
долговечность записи отключена, порт отличается от development-стека, поэтому
оба работают одновременно. В сеть тесты не ходят.

Один нюанс изоляции пришлось учесть явно. `CurrentUserMiddleware` из django CMS
хранит текущего пользователя в thread-local и не очищает его после ответа. При
`CMS_PERMISSION=True` пользователь из предыдущего теста доживал до следующего, и
сигнал `post_save` записывал `PageUser` со ссылкой на уже откаченного
`auth_user`. Автоиспользуемая фикстура в `tests/conftest.py` сбрасывает это
значение до и после каждого теста.
