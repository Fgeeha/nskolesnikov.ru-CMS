# AGENTS.md

## 1. Назначение проекта

Этот репозиторий содержит персональный сайт-портфолио Python-разработчика, построенный на Django и django CMS.

Основные цели:

1. Публичное представление разработчика.
2. Публикация проектов, опыта, навыков и статей.
3. Управление содержимым без изменения исходного кода.
4. Воспроизводимый локальный и production-запуск.
5. Простая поддержка одним разработчиком.
6. Высокое качество кода без избыточной архитектуры.

Этот файл обязателен для всех изменений в репозитории.

## 2. Приоритет правил

При конфликте требований используй следующий приоритет:

1. Безопасность и сохранность данных.
2. Явное задание пользователя.
3. Настоящий `AGENTS.md`.
4. Существующая архитектура проекта.
5. Тесты и документированные контракты.
6. Общие рекомендации фреймворков.
7. Личные предпочтения исполнителя.

Не обходи правила проекта ради более быстрого завершения задачи.

## 4. Управление Python и зависимостями

`uv` является единственным менеджером Python-окружения и зависимостей проекта.

Обязательные файлы:

```text
.python-version
pyproject.toml
uv.lock
```

Разрешённые команды:

```bash
uv python pin 3.13
uv add package-name
uv add --dev package-name
uv remove package-name
uv lock
uv sync
uv sync --frozen
uv run command
uv tree
```

Запрещено:

```bash
pip install ...
python -m pip install ...
poetry add ...
pipenv install ...
```

Не редактируй `uv.lock` вручную.

После изменения зависимостей:

1. Измени зависимости через `uv add` или `uv remove`.
2. Обнови `uv.lock`.
3. Выполни `uv sync`.
4. Запусти проверки проекта.
5. Закоммить `pyproject.toml` и `uv.lock` вместе.

`requirements.txt` не является источником зависимостей. Не создавай его без отдельной необходимости для внешней интеграции.

Git отвечает за историю исходного кода. `uv` отвечает за Python, окружение, зависимости и lock-файл.

## 5. Структура репозитория

Основные каталоги:

```text
src/        Python-код, Django-проект, приложения, шаблоны и статика
tests/      общие unit- и integration-тесты
infra/      Docker, Compose, Nginx, entrypoint и инфраструктурные скрипты
docs/       архитектурная и эксплуатационная документация
```

### Обязательные ограничения

* Весь Python-код приложения размещается в `src/`.
* `manage.py` размещается в `src/manage.py`.
* Django project package размещается в `src/config/`.
* Django apps размещаются в `src/apps/`.
* Общие шаблоны размещаются в `src/templates/`.
* Исходная статика размещается в `src/static/`.
* Dockerfile размещаются только в `infra/docker/`.
* Compose-файлы размещаются только в `infra/compose/`.
* Конфигурация Nginx размещается только в `infra/nginx/`.
* Инфраструктурные shell-скрипты размещаются в `infra/`.

Не создавай второй Django-проект, альтернативный каталог приложений или параллельную структуру конфигурации.

## 6. Django-приложения

Базовое разделение ответственности:

```text
src/apps/core/        общая инфраструктура приложения
src/apps/portfolio/   проекты, навыки, опыт, образование и профиль
src/apps/blog/        статьи, категории и теги
src/apps/contact/     обращения и контактная форма
```

Новое приложение создавай только тогда, когда появляется самостоятельная предметная область.

Не создавай приложение для одной модели или одной служебной функции.

## 7. Настройки Django

Настройки разделены на:

```text
src/config/settings/base.py
src/config/settings/development.py
src/config/settings/production.py
src/config/settings/test.py
```

Правила:

* общие настройки находятся в `base.py`;
* локальные настройки находятся в `development.py`;
* усиленные настройки безопасности находятся в `production.py`;
* тестовые упрощения находятся в `test.py`;
* секреты читаются только из переменных окружения;
* значения production-секретов не должны иметь небезопасных fallback;
* `DEBUG` не должен быть включён в production;
* development не должен случайно включать HSTS;
* production должен учитывать работу за reverse proxy;
* значения hosts и trusted origins не должны быть захардкожены под один домен.

Не создавай `local_settings.py`.

## 9. Модели

Модели должны:

* иметь понятные имена;
* иметь `verbose_name` и `verbose_name_plural`;
* иметь корректный `__str__`;
* использовать осмысленные `related_name`;
* задавать сортировку через `Meta.ordering`, когда она стабильна;
* использовать ограничения базы для критичных инвариантов;
* использовать индексы для частых фильтров;
* содержать timestamps только там, где они нужны;
* хранить URL в `URLField`;
* использовать `SlugField` для публичных адресов;
* не хранить вычисляемые данные без необходимости;
* не содержать presentation-логику.

Slug должен быть стабильным и уникальным в пределах публичного URL.

Не меняй существующие slug автоматически при каждом сохранении объекта.

## 10. Миграции

После изменения моделей обязательно выполни:

```bash
uv run python src/manage.py makemigrations
uv run python src/manage.py migrate
uv run python src/manage.py makemigrations --check --dry-run
```

Правила:

* миграции коммитятся вместе с изменением моделей;
* миграции не редактируются после применения в общем окружении без веской причины;
* удаление данных выполняется отдельными безопасными миграциями;
* большие data migration должны быть идемпотентными или пакетными;
* импорт демонстрационных данных не выполняется миграциями;
* не объединяй миграции автоматически без явной необходимости;
* не удаляй старые миграции ради «чистоты».

Перед необратимой миграцией явно опиши риск.

## 11. django CMS

django CMS управляет структурой страниц и редактируемыми блоками.

Правила:

* не хардкодь содержимое главной страницы в Python;
* используй placeholders для композиции страниц;
* выноси повторно используемые визуальные блоки в CMS-плагины;
* не дублируй данные моделей в плагинах;
* плагин должен либо выбирать существующие объекты, либо хранить параметры отображения;
* не связывай логику с translated title страницы;
* не связывай логику с числовым primary key CMS-страницы;
* проверяй отображение в edit и preview mode;
* учитывай draft и published состояния;
* не обходи CMS permissions;
* не выполняй тяжёлые запросы отдельно для каждого экземпляра плагина;
* используй `select_related` и `prefetch_related`;
* добавляй тесты регистрации и рендеринга плагина.

При изменении шаблонов CMS проверяй:

```bash
uv run python src/manage.py cms check
```

## 13. Views и URL

Правила:

* URL имеют namespace;
* публичные URL используют slug;
* имена URL стабильны;
* redirects применяются явно;
* GET-запросы не изменяют данные;
* POST-запросы защищены CSRF;
* формы проверяются сервером;
* права доступа проверяются до выполнения изменения;
* 404 используется вместо утечки существования закрытого объекта;
* пагинация применяется к потенциально большим спискам;
* canonical URL формируется корректно.

Class-based view не является обязательной. Выбирай самый понятный вариант.

## 14. ORM и производительность

Избегай N+1 запросов.

Применяй:

```python
select_related(...)
prefetch_related(...)
Prefetch(...)
only(...)
defer(...)
```

только при наличии понятной причины.

Перед оптимизацией проверь реальный queryset.

Не используй raw SQL, если Django ORM выражает запрос достаточно понятно.

Для составных изменений используй:

```python
transaction.atomic()
```

Не держи транзакцию открытой во время сетевых запросов, отправки email или тяжёлой обработки файлов.

## 15. Сервисы и бизнес-логика

Не создавай сервисный слой автоматически для каждого действия.

Сервис оправдан, когда:

* операция используется несколькими интерфейсами;
* операция состоит из нескольких изменений;
* нужна транзакционная граница;
* логика плохо помещается в model method или form;
* требуется изолированное тестирование;
* есть взаимодействие с внешним сервисом.

Не размещай сложную бизнес-логику:

* в шаблонах;
* в `save()` без необходимости;
* в signals без явного обоснования;
* в admin actions, если она нужна вне admin.

Signals используй только для слабо связанных побочных действий. Критичную логику вызывай явно.

## 21. Docker

Вся Docker-инфраструктура находится в `infra/`.

Правила Dockerfile:

* multi-stage build;
* минимальный runtime image;
* непривилегированный пользователь;
* зависимости через `uv`;
* lock-файл обязателен;
* production sync выполняется с `--frozen`;
* build-зависимости не остаются в runtime;
* секреты не передаются через `ARG`;
* healthcheck не зависит от внешнего интернета;
* entrypoint использует `set -eu`;
* shell-скрипты корректно передают сигналы через `exec`;
* не очищай volumes автоматически.

Запрещено:

* помещать `.env` в image;
* запускать приложение от root;
* использовать `latest` для критичных production-образов;
* устанавливать зависимости при каждом запуске контейнера;
* выполнять `flush`;
* выполнять автоматический `createsuperuser`;
* удалять volume при обычной остановке;
* публиковать порт PostgreSQL в production без необходимости.

## 22. Docker Compose

Development Compose должен содержать минимум:

* `web`;
* `db`.

Production Compose должен содержать минимум:

* `web`;
* `db`;
* `nginx`.

Правила:

* PostgreSQL имеет healthcheck;
* web ожидает доступности базы;
* media и database используют named volumes;
* development поддерживает удобную работу с исходниками;
* production не монтирует весь репозиторий поверх приложения;
* наружу публикуется только необходимый порт;
* production использует restart policy;
* пароли передаются через environment или secrets-механизм;
* имена сервисов стабильны.

Основные команды:

```bash
docker compose -f infra/compose/compose.dev.yml up --build
docker compose -f infra/compose/compose.dev.yml down
docker compose -f infra/compose/compose.dev.yml logs -f web

docker compose -f infra/compose/compose.prod.yml up -d --build
docker compose -f infra/compose/compose.prod.yml ps
docker compose -f infra/compose/compose.prod.yml logs -f
```

Не используй `down -v`, если пользователь явно не запросил удаление данных.

## 25. Ruff

Ruff используется для lint и format.

Не отключай правило глобально ради одного нарушения.

Порядок решения:

1. Исправь код.
2. Если исправление ухудшает код, добавь точечный `noqa`.
3. Объясни нетривиальное исключение комментарием.
4. Глобальное исключение добавляй только для устойчивой особенности проекта.

Не выполняй массовое форматирование несвязанных файлов.

## 26. Типизация

* utility functions;
* selectors;
* management commands;
* интеграции;
* нетривиальные методы;
* публичные функции.

* не содержать захардкоженных production-секретов.

Команда `seed_demo` должна использовать `update_or_create` или другой идемпотентный подход.

## 29. Логирование

Используй стандартный модуль `logging`.

Запрещено:

* `print()` в production-коде;
* логирование паролей;
* логирование токенов;
* логирование cookie;
* логирование полного содержимого форм;
* скрытие traceback неожиданных ошибок.

Логи должны помогать найти причину проблемы, но не раскрывать персональные или секретные данные.

## 30. Безопасность

При каждом изменении учитывай:

* CSRF;
* XSS;
* SQL injection;
* open redirects;
* загрузку файлов;
* права CMS;
* доступ к черновикам;
* секреты;
* secure cookies;
* trusted origins;
* host validation;
* rate limiting контактной формы;
* зависимости с известными уязвимостями.

Не используй `mark_safe` для непроверенного контента.

Не отключай CSRF ради упрощения.

Не разрешай произвольные redirect URL.

## 31. Производительность

Не оптимизируй без причины, но избегай очевидных проблем:

* N+1;
* запросов к БД из циклов шаблонов;
* загрузки всех объектов без пагинации;
* больших изображений;
* тяжёлого JavaScript;
* блокирующих внешних ресурсов;
* повторных вычислений в каждом CMS-плагине;
* неоправданных запросов в context processor.

Кеширование добавляй только после определения безопасных границ инвалидирования.

## 32. Документация

При изменении пользовательского или эксплуатационного поведения обновляй документацию.

README должен оставаться воспроизводимым.

Проверяй, что команды:

* используют актуальные пути;
* используют `uv`;
* используют актуальные Compose-файлы;
* не требуют неописанных действий;
* не содержат секретов;
* не удаляют данные.

Архитектурные решения описывай в `docs/architecture.md`.

Deployment описывай в `docs/deployment.md`.

Работу с CMS описывай в `docs/content-management.md`.

## 33. Git

Перед изменениями проверь:

```bash
git status --short
git branch --show-current
```

Не перезаписывай пользовательские изменения.

Не выполняй без явного запроса:

```bash
git reset --hard
git clean -fd
git push
git push --force
git rebase
git commit --amend
git tag
```

Не удаляй чужие ветки.

Не включай в коммит несвязанные изменения.

## 34. Коммиты

Используй Conventional Commits:

```text
feat: add project detail pages
fix: prevent unpublished articles in sitemap
test: cover portfolio cms plugin
refactor: simplify contact form service
docs: document production deployment
chore: update development tooling
```

Сообщение должно описывать изменение, а не процесс работы.

Не добавляй в commit message, тело коммита, pull request или trailers:

* сведения о происхождении кода от автоматизированных инструментов;
* рекламные подписи;
* служебное авторство инструментов;
* `Co-Authored-By`, не относящийся к реальному человеку-автору;
* фразы вида «generated with»;
* эмодзи или подписи ботов.

Упоминание AI/ML допустимо только как предметная область портфолио, проекта или статьи.

Не создавай коммит без явного запроса, если задача заключалась только в подготовке изменений.

## 35. Рабочий процесс

Для каждой задачи:

1. Прочитай запрос.
2. Прочитай этот файл.
3. Проверь состояние Git.
4. Изучи связанные файлы.
5. Найди существующие соглашения проекта.
6. Составь небольшой план.
7. Сделай минимально достаточное изменение.
8. Добавь или обнови тесты.
9. Запусти релевантные проверки.
10. Проверь diff.
11. Обнови документацию.
12. Подготовь фактический отчёт.

Не переписывай рабочий код без причины.

Не расширяй scope задачи скрытыми улучшениями.

Не откладывай очевидные исправления, без которых задача не работает.

## 36. Работа с ошибками

При ошибке:

1. Сохрани точную команду.
2. Изучи полный traceback.
3. Найди первопричину.
4. Исправь первопричину, а не симптом.
5. Повтори минимальную проверку.
6. Запусти полный релевантный набор проверок.
7. Опиши результат.

Не подавляй исключения через пустой `except`.

Запрещено:

```python
try:
    ...
except Exception:
    pass
```

Если исключение намеренно игнорируется, укажи конкретный тип и причину.

## 37. Запрещённые практики

Не допускаются:

* секреты в Git;
* зависимости без записи в `pyproject.toml`;
* ручное изменение `uv.lock`;
* production на SQLite;
* код приложения вне `src/`;
* Dockerfile вне `infra/`;
* огромные views;
* бизнес-логика в шаблонах;
* необоснованные signals;
* необоснованные service/repository слои;
* отключение CSRF;
* `DEBUG=True` в production;
* запуск контейнера от root;
* автоматическое удаление volumes;
* автоматический `flush`;
* автоматическое создание суперпользователя с известным паролем;
* непроверенные внешние скрипты;
* CDN-зависимость для критической функциональности;
* сетевые обращения в тестах;
* изменение данных через GET;
* скрытые миграции;
* фиктивные результаты тестов;
* заявления о выполненных командах без их запуска.

## 38. Критерии завершённости

Изменение считается завершённым, когда:

* задача реализована;
* архитектура проекта сохранена;
* код находится в правильных каталогах;
* миграции созданы;
* тесты добавлены или обоснованно не нужны;
* Ruff проходит;
* форматирование проходит;
* Django check проходит;
* django CMS check проходит;
* проверка миграций проходит;
* pytest проходит;
* документация актуальна;
* diff не содержит посторонних изменений;
* секреты не добавлены;
* фактические ограничения перечислены.

## 39. Итоговый отчёт

После работы сообщи:

```text
Реализовано:
- ...

Изменённые файлы:
- ...

Архитектурные решения:
- ...

Проверки:
- команда — результат

Не выполнено:
- ...

Известные ограничения:
- ...

Следующие шаги:
- ...
```

Результаты должны быть фактическими.

Не называй проверку успешной, если она не запускалась или завершилась ошибкой.
